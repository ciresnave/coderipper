---
**SEC-002 now waives seven history-only false positives of `ciresnave/commy-sdk-rust`, visibly (Info, never silent).** Each entry names one gitleaks finding by repository, full commit SHA, file, rule and line, and nothing else; expiry 2027-02-17. Each commit was read by the lane before its entry was written, and none holds a credential or key material. Three kinds: `generic-api-key` on a made-up password in a unit test that checks `Debug` output hides secrets (`src/message.rs`: `c6722fca` line 479 on main, its pre-squash branch commit `3946acc2` line 464, and `4e7b7b09` line 479 on `refs/pull/5/head`); `private-key` on placeholder text between PEM markers in a demo helper that never held a key (`src/examples_support.rs`: `c17d127d` line 142 and `80ab969f` line 145 on main, `debf24bb` line 142 on a pull-request ref), removed from the tree in 0.19.2; and `generic-api-key` on a roadmap row that quotes that test fixture while recording that it is not a secret (`ROADMAP.md`, `54422f26` line 17, a pull-request ref). Pull-request refs are history and stay scanned; they cannot be deleted, so they are waived instead. The scan on a single-branch clone of main went from three Critical findings to three waived Info findings. A test proves the entries match exactly these seven fingerprints and that the next or previous line, another file, another rule, another commit or another repository stays reported.
**Corrected in the same change (a flaw in 0.47.13's stale-waiver check):** an entry whose commit is in the repository but is reachable from no ref (an object left behind after a branch was deleted, not yet garbage-collected) is not scanned by gitleaks, so its waiver names nothing to find; the check treated it as present and reported a Medium "waiver names a finding that no longer exists". It now counts a commit as scanned only if a ref or `HEAD` reaches it. Test `a_commit_left_over_after_its_branch_was_deleted_is_not_scanned` (reverting to the object-exists test fails it).
