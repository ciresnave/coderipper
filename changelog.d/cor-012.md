**COR-012 is built in part (Rust, opt-in): an `unsafe impl Send` or `unsafe impl Sync` that the type's own fields contradict.** A new catalog record (`rules/cor.toml`; roadmap item 11, `docs/rules/REMAINING.md`; extends `SEC-005`, which asks only for a `SAFETY` comment). Each Rust file is parsed with `syn`; each `unsafe impl Send` and `unsafe impl Sync` is matched by name to the one struct, enum or union of that name in the package and reported once (Medium, Medium confidence) when a field type names `Rc`, when a `Sync` impl covers a type with a `Cell` or `RefCell` field, or when an impl type parameter has no trait bound at all and a field other than a `PhantomData` uses the matching parameter (the impl then also covers `W<Rc<u8>>`). A raw pointer field is not reported: it is the usual reason for the impl. Opt-in: it runs when named (`coderipper check COR-012`), in no profile, advisory. Not seen: types from another package or a macro, two types of one name (skipped), a cell or `Rc` behind an alias, a too-weak bound, a bound on a project trait (`T: Element` may imply `Send`; any bound but `Sized` counts as one), an impl made sound by a lock. Evidence: `check COR-012` over every non-worktree checkout under `C:\Projects` that tracks `.rs` files (69 checkouts, 2026-11-14, binary built from this branch): 0 findings (one checkout tracks no package source). A denominator: 260 lines of `unsafe impl .. Send/Sync` in 10 checkouts (`git grep`; `fuel` and `fuel-ign1` are the same code). The rule as first written reported 4 sites, all false: `unsafe impl<T: Element> Send for X<T>` in baracuda (2) and bonefish (2), where `Element` is the project's own sealed trait of plain numbers; the unbounded-parameter check now ignores a parameter that has any bound, a change fitted to those 4. The rule has not met a real defect in the portfolio; it is exercised by 9 unit tests and a conformance pair (an `Rc` field behind `Send` reported at its impl line; an `Arc` and a `T: Send` parameter clean).
