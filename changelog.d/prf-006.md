**PRF-006 is built (opt-in): a performance exception names the benchmark that justified it.** Roadmap item 11 (PM ruling 2026-11-15: a comment marker, no config key; Info, low confidence, opt-in, silent without markers). The convention a repository adopts by writing it: a source comment that **begins** with `PERF-EXCEPTION:` and gives a benchmark reference on its own line or in the comment text of the next two lines: an `http(s)` link, a path with a `bench`, `benches`, `benchmark` or `benchmarks` directory (`benches/decode.rs`), or a `bench::` name, as in `// PERF-EXCEPTION: get_unchecked in the hot loop, see benches/decode.rs`. A marker with none is one Info finding per file, at the first such marker, with the count. A repository with no marker is not applicable. Comment families are those of `RDB-008` (`//` and `/* */`, `#`, `--`), whose comment reader the rule shares (`rdb008.rs` items made `pub(super)`, no change in behaviour). The convention is documented in `docs/rules/prf.md` and the README row. Not judged: whether a link resolves or the benchmark shows what the comment says, a performance deviation that carries no marker, a reference above the marker. Evidence: `git grep PERF-EXCEPTION` at `HEAD` over the 81 non-worktree checkouts under `C:\Projects` (2026-11-15) finds the text nowhere, so by design the rule reports nothing on them and is silent until a project adopts the marker (a looser count, comments naming `get_unchecked`, `inline(always)`, a hot loop or hot path, finds 64 candidate sites in 10 checkouts that carry no marker, which is the adoption gap, not a finding); it is exercised by 7 unit tests and a conformance pair (a marker naming `benches/sum.rs` clean, a marker with no reference reported at its line).
